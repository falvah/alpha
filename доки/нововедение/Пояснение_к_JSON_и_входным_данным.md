# Пояснение к входным данным и JSON-ответу скоринговой карты

Данный документ описывает структуру входного JSON от бэкенда, процесс преобразования в модели, а также расшифровку полей JSON-ответа на примере `good_mature.json`.

## 1. Структура входного JSON

Входной payload передаётся в `score_payload()` или `LoanRequest.from_payload()`. Ключи могут быть русскими или английскими — адаптер (`models.py`) ищет первый подходящий вариант через `_pick()`.

### 1.1. `заявка` / `application`

Данные самой заявки.

| Ключ (рус/англ) | Тип | Обязательное | Пояснение |
| --- | --- | --- | --- |
| `сумма` / `amount` | number/string | Да | Сумма кредита. Парсится через `parse_decimal()` (поддерживает пробелы, запятую, `руб.`). Должна быть > 0. |
| `срок` / `term`, `term_months` | number/string | Да | Срок кредита в месяцах. Должен быть > 0. |
| `форма` / `legal_form`, `form` | string | Нет | ОПФ. Нормализуется в `normalize_legal_form()` -> `ооо` / `ао` / `ип`. |
| `название` / `name` | string | Нет | Наименование компании. |
| `в_лице` / `signatory` | string | Нет | Подписант. |
| `адрес` / `address` | string | Нет | Юридический адрес (не сверяется с обогащением). |
| `инн` / `inn` | string | Нет | ИНН. |
| `огрн` / `ogrn` | string | Нет | ОГРН. |
| `цель` / `purpose` | string | Нет | Цель кредита. Классифицируется `classify_purpose()` в `working_capital` / `equipment` / `refinancing` / `investment` / `other`. |
| `ссылка_на_документ` / `document_url` | string | Нет | Ссылка на документ. |

### 1.2. `обогащение` / `enrichment`

Данные обогащения (проверки, регистрация, кредитная история, собственность).

| Ключ (рус/англ) | Тип | Обязательное | Пояснение |
| --- | --- | --- | --- |
| `дата_регистрации` / `registration_date` | string/date | Нет | Дата регистрации ЮЛ. Должна быть <= даты оценки. Используется для расчёта `months_since_registration`. |
| `оквэд` / `okved` | string | Нет | Код ОКВЭД. Берутся первые 2 цифры для `okved_section`. |
| `адрес_массовый` / `address_mass` | `да`/`нет`/`пусто`/bool/int | Нет | Массовый адрес регистрации. Является **жёстким стопом** при `true`. |
| `адрес_недостоверный` / `address_unreliable` | `да`/`нет`/`пусто`/bool/int | Нет | Недостоверный адрес. Жёсткий стоп при `true`. |
| `руководитель_дисквалиф.` / `руководитель_дисквалифицирован` / `director_disqualified` | `да`/`нет`/`пусто`/bool/int | Нет | Дисквалифицированный руководитель. Жёсткий стоп при `true`. |
| `руководитель_массовый` / `director_mass` | `да`/`нет`/`пусто`/bool/int | Нет | Массовый руководитель. Жёсткий стоп при `true`. |
| `юрлиц_у_руководителя` / `companies_per_director` | number/string | Нет | Количество ЮЛ у руководителя. При > 20 — жёсткий стоп `MASS_MANAGEMENT`. |
| `число_связанных` / `related_parties_count` | number/string | Нет | Количество связанных сторон. Может быть вложено в `связанные_стороны`/`related_parties`. |

#### Вложенные блоки обогащения

##### `кредитная_история` / `credit_history`

| Ключ (рус/англ) | Тип | Обязательное | Пояснение |
| --- | --- | --- | --- |
| `есть_история` / `has_history` | `да`/`нет`/`пусто`/bool/int | **Да** (обязателен по `required_features.all`) | Наличие кредитной истории. При отсутствии — `MISSING_REQUIRED_DATA`. |
| `макс_просрочка_12м` / `max_overdue_12m` | number/string | Нет | Максимальная просрочка за 12 мес, дни. При > 90 — жёсткий стоп `CRITICAL_OVERDUE`. |
| `активных_кредитов` / `active_loans` | number/string | Нет | Количество активных кредитов. |

##### `собственность` / `ownership`

| Ключ (рус/англ) | Тип | Обязательное | Пояснение |
| --- | --- | --- | --- |
| `число_владельцев` / `owners_count` | number/string | Нет | Количество владельцев бизнеса. |
| `номинальный_владелец` / `nominal_owner` | `да`/`нет`/`пусто`/bool/int | Нет | Номинальный владелец. Жёсткий стоп при `true`. |

##### `связанные_стороны` / `related_parties`

| Ключ (рус/англ) | Тип | Обязательное | Пояснение |
| --- | --- | --- | --- |
| `число_связанных` / `related_parties_count` | number/string | Нет | Количество связанных сторон. |

### 1.3. `документ` / `document`

Определяет ветку скоринга. **Нельзя одновременно заполнять поля обеих веток** — при этом выбрасывается `InputDataError`.

#### Ветка `mature` (≥ 12 месяцев поступлений)

Используется, если заполнены хотя бы одно из полей ниже.

| Ключ (рус/англ) | Тип | Обязательное | Пояснение |
| --- | --- | --- | --- |
| `месяцев_с_поступлениями` / `months_with_inflows` | number/string | **Да** (для ветки `mature`) | Количество месяцев с поступлениями на счёт. |
| `средний_приход` / `avg_monthly_inflow` | number/string | **Да** (для ветки `mature`) | Среднемесячные поступления на счёт. Не прибыль. Для расчёта лимита используется `avg_monthly_inflow * inflow_haircut` (0,8). |
| `вариативность` / `variability` | number/string | Нет | Коэффициент вариации поступлений (std/mean), безразмерный. |

#### Ветка `young` (< 12 месяцев)

Используется, если заполнены хотя бы одно из полей ниже.

| Ключ (рус/англ) | Тип | Обязательное | Пояснение |
| --- | --- | --- | --- |
| `есть_поручительство` / `has_guarantee` | `да`/`нет`/`пусто`/bool/int | Нет | Наличие поручительства. |
| `доход_поручителя` / `guarantor_income` | number/string | Нет | **Годовой** доход поручителя. В расчётах делится на 12. |
| `стоимость_залога` / `collateral_value` | number/string | Нет | Рыночная стоимость залога. Учитывается по LTV из `policy.collateral_ltv`. |
| `тип_залога` / `collateral_type` | string | Нет | Тип залога. Нормализуется в `недвижимость` / `транспорт` / `оборудование` / `прочее`. |

Если `document` отсутствует, пустой или все поля ветки `"пусто"` — ветка не определяется, результатом будет отказ `DOCUMENT_MISSING`.

### 1.4. `служебное` / `service`

Служебные данные для скоринга.

| Ключ (рус/англ) | Тип | Обязательное | Пояснение |
| --- | --- | --- | --- |
| `дата_оценки` / `valuation_date` | string/date | **Да** | Дата оценки заявки. Используется для расчёта возраста компании. |
| `версия_карты` / `card_version` | string | Нет | Версия карты, по которой бэкенд ожидает расчёт. При отличии от загруженной — флаг `CARD_VERSION_MISMATCH`. |

### 1.5. Нормализация входных данных

Модуль `normalization.py` отвечает за приведение значений:

| Функция | Назначение |
| --- | --- |
| `parse_tristate()` | `"да"/"нет"/"пусто"`, `bool`, `0/1` -> `True`/`False`/`None`. Неизвестное значение вызывает `InputDataError`. |
| `parse_decimal()` | Парсинг сумм. Удаляет пробелы, неразрывные пробелы, `руб.`, `₽`, заменяет `,` на `.`, использует `Decimal`. Отвергает `NaN`/`Infinity`. |
| `parse_int()` / `parse_count()` | Целые числа. `parse_count()` дополнительно проверяет >= 0. |
| `parse_date()` | Парсинг дат (`YYYY-MM-DD`, `DD.MM.YYYY`, `DD/MM/YYYY`, ISO с таймзоной). |
| `months_between()` | Расчёт полных календарных месяцев между датами. |
| `normalize_text()` | Нижний регистр, `ё` -> `е`, пробелы, подчёркивания. |
| `normalize_legal_form()` / `normalize_collateral_type()` | Канонизация ОПФ и типа залога. |
| `classify_purpose()` | Классификация свободного текста цели кредита по ключевым словам. |
| `parse_okved_section()` | Первые две цифры ОКВЭД. |

**Принцип `fail fast`:** некорректный формат или неизвестное значение три-стейта вызывают `InputDataError`, а не приводятся к `None`.

## 2. JSON-ответ скоринговой карты

Ниже описание всех полей ответа на примере `good_mature.json`.

### 2.1. Базовые поля решения

| Поле | Тип | Пояснение |
| --- | --- | --- |
| `decision` | string | Итоговое решение: `approve` / `decline` / `review`. |
| `is_approved` | bool | `true` только если `decision == "approve"`. |
| `requires_manual_review` | bool | `true` только если `decision == "review"`. |
| `branch` | string | Ветка: `mature` или `young`. |
| `requested_amount` | float | Запрошенная сумма из заявки. |
| `approved_amount` | float \| null | Одобренная сумма. При отказе — `null`. Может быть меньше запрошенной. |
| `limit_amount` | float \| null | Максимально доступный расчётный лимит. |
| `annual_rate` | float \| null | Годовая ставка, округлённая до 0,5 п.п. При отказе — `null`. |
| `monthly_payment` | float \| null | Аннуитетный платёж. При отказе — `null`. |
| `term_months` | int | Срок из заявки. |
| `currency` | string | Валюта (`RUB`). |
| `pd` | float | Вероятность дефолта за 12 мес. `PD = sigmoid(logit)`. Возвращается всегда. |
| `logit` | float | `intercept + Σ points` (intercept = -2,50). |
| `score_points` | float | Сумма баллов по применимым факторам. |
| `data_coverage` | float | Доля заполненных факторов по весам. |
| `card_version` | string | Версия использованной карты. |
| `reason_codes` | string[] | Машинные коды причин. |
| `reasons` | object[] | Причины в читаемом виде `{"code", "title", "type"}`. |
| `flags` | string[] | Доп. пометки: `AMOUNT_REDUCED`, `THIN_CREDIT_HISTORY`, `HIGH_PTI`, `YOUNG_BUSINESS`, `PARTIAL_DATA`, `NO_COLLATERAL`, `COLLATERAL_SHORTFALL`, `GREY_ZONE`, `CARD_VERSION_MISMATCH`. |

### 2.2. Факторы (`factors`)

| Поле | Тип | Пояснение |
| --- | --- | --- |
| `id` | string | ID фактора из `card.yaml`. |
| `title` | string | Название фактора. |
| `value` | any | Значение, использованное при расчёте (`true/false` -> `"да"/"нет"`). |
| `bin` | string | Бин, в который попало значение. При пропуске — `"нет данных"`. |
| `points` | float | Баллы фактора (+ риск / - снижение риска). |
| `weight` | float | Вес для `data_coverage`. |
| `present` | bool | Признак наличия значения. |

### 2.3. Топ-факторы

| Поле | Тип | Пояснение |
| --- | --- | --- |
| `top_risk_factors` | object[] | Топ-5 с `points > 0` по убыванию баллов. |
| `top_mitigants` | object[] | Топ-5 с `points < 0` по убыванию модуля. |

## 3. Как работает логика принятия решения

1. **Адаптер** — парсинг русских ключей, нормализация типов.
2. **Определение ветки** — по заполненным полям `документ`. Если обе ветки заполнены — ошибка. Если ни одной — `DOCUMENT_MISSING`.
3. **Построение признаков** — производные (`months_since_registration`, `pti`, `guarantor_pti`, `collateral_coverage`, `guarantee_coverage`).
4. **Оценка факторов** — подбор бина по карте, суммирование баллов.
5. **Расчёт PD** — `logit = intercept + sum(points)`, `PD = sigmoid(logit)`.
6. **Проверки** — жёсткие стопы, обязательные (`required_features`), критичные проверки (`critical_features`), покрытие данных.
7. **Решение по PD** — если заблокировано/стоп/плохие данные — `decline`. Иначе сравнение с `max_pd` (и `review_pd` при включении).
8. **Лимит/ставка** — расчёт по PTI и/или LTV, ставка по сетке + дисконт за залог, округления.
9. **Сборка ответа** — формирование `Decision.to_dict()` с причинами, флагами, факторами.

## 4. Важные особенности

- **"пусто" vs "нет"** — принципиально разные. `пусто` = нет данных (штраф + снижение покрытия + блокировка при критичных проверках), `"нет"` = конкретный факт.
- **PD всегда считается** — даже при отказе.
- **Проверка по reference_rate** — PTI считается по 24% для консервативности и избежания цикла.
- **Доход поручителя годовой** — в ветке `young` делится на 12.
- **Аннуитетные расчёты** — через `Decimal` для денег, округления до копеек/10 000 ₽.
- **Детерминизм** — одинаковый вход даёт одинаковый выход.

## 5. Тест проверки данных при получении (фейковый слой обогащения)

В реальной интеграции проверки по массовым адресам, недостоверности адреса, дисквалификации руководителя, массовости руководителя, номинальному владельцу и др. выполняются внешними сервисами (ФНС, ЕГРЮЛ, реестры и т.п.). В текущем проекте они **не интегрированы** — скоринг ожидает, что эти значения уже пришли в блоке `обогащение`.

Для тестов и отладки можно воспроизвести внешние проверки в сокращённом виде через **фейковые функции**. Суть — имитировать ответ обогащения, сохраняя структуру, совместимую с `LoanRequest.from_payload()` и скорингом.

### 5.1. Принцип работы

1. На вход получаем сырые данные заявки (например, адрес компании, ФИО/данные руководителя).
2. Прогоняем через фейковые функции проверки.
3. Формируем блок `обогащение` с полями, которые ожидает модель (`адрес_массовый`, `адрес_недостоверный`, `руководитель_дисквалиф.`, `руководитель_массовый`, `юрлиц_у_руководителя`, `номинальный_владелец` и др.).
4. Собираем полный payload и передаём в скоринг.

Никакие внешние HTTP-запросы при этом не нужны. Фейковые функции работают только на синтетических списках/правилах.

### 5.2. Пример фейковых функций

```python
# fake_enrichment.py
MASS_ADDRESSES = {
    "г. Москва, ул. Тверская, д. 1",  # пример из тестового набора
    "г. Санкт-Петербург, Невский пр., д. 100",
}

DISQUALIFIED_DIRECTORS = {"Иванов И.И."}
MASS_DIRECTORS = {"Петров П.П."}
NOMINAL_OWNERS = {"Сидоров С.С."}

def check_address_mass(address: str | None) -> bool | None:
    if not address:
        return None
    return address.strip() in MASS_ADDRESSES

def check_address_unreliable(address: str | None) -> bool | None:
    if not address:
        return None
    # Упрощённая логика для теста
    if "фейковый" in address.lower():
        return True
    return False

def check_director_disqualified(full_name: str | None) -> bool | None:
    if not full_name:
        return None
    return full_name.strip() in DISQUALIFIED_DIRECTORS

def check_director_mass(full_name: str | None) -> bool | None:
    if not full_name:
        return None
    return full_name.strip() in MASS_DIRECTORS

def check_companies_per_director(full_name: str | None) -> int | None:
    if full_name and full_name.strip() in MASS_DIRECTORS:
        return 25  # > 20 -> сработает стоп MASS_MANAGEMENT
    return 2

def check_nominal_owner(owner_name: str | None) -> bool | None:
    if not owner_name:
        return None
    return owner_name.strip() in NOMINAL_OWNERS
```

### 5.3. Сборка блока обогащения

```python
def build_enrichment_fake(app: dict) -> dict:
    address = app.get("адрес") or app.get("address")
    director = app.get("в_лице") or app.get("signatory")
    # для примера берём первого владельца
    owner = "Иванов И.И."

    return {
        "оквэд": "46.90",
        "адрес_массовый": "да" if check_address_mass(address) else "нет",
        "адрес_недостоверный": "да" if check_address_unreliable(address) else "нет",
        "руководитель_дисквалиф.": "да" if check_director_disqualified(director) else "нет",
        "руководитель_массовый": "да" if check_director_mass(director) else "нет",
        "юрлиц_у_руководителя": check_companies_per_director(director),
        "дата_регистрации": "2019-03-12",
        "кредитная_история": {
            "есть_история": "да",
            "макс_просрочка_12м": 0,
            "активных_кредитов": 2,
        },
        "собственность": {
            "число_владельцев": 2,
            "номинальный_владелец": "да" if check_nominal_owner(owner) else "нет",
        },

    }
```

### 5.5. Важные замечания

- **Сохранить смысл интеграции.** Фейк должен возвращать ровно те же типы/значения, что и реальный сервис (`да`/`нет`/`пусто`, числа). Скоринг не меняется.
- **Тестовые списки** — хранить отдельно (например, `tests/fake_enrichment_data.py`). Это позволяет менять правила без правок в самой карте/модели.
- **"пусто" vs "нет".** Если проверка не проводилась — можно вернуть `"пусто"`. В таком случае для полей из `policy.critical_features` скоринг блокирует одобрение с `CRITICAL_DATA_MISSING`.
- **Жёсткие стопы срабатывают первыми.** Как и в реальности, `ADDRESS_MASS`, `DIRECTOR_DISQUALIFIED`, `NOMINAL_OWNER` и др. приводят к отказу независимо от баллов.
- **Синтетические данные.** Используйте только тестовые адреси/ФИО, чтобы избежать случайного совпам
