# Безопасность

Кабинет использует ролевую модель, серверную валидацию и транзакционные переходы заявки. Базовые механизмы спроектированы по [документации безопасности Django](https://docs.djangoproject.com/en/5.2/topics/security/) и [deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

| Риск | Реализованная мера | Проверка |
|---|---|---|
| Чужая заявка или PDF, IDOR | Серверный queryset по владельцу на каждом чтении; сервисы повторно проверяют владельца; клиент получает 404 | Интеграционный тест чужой заявки, API и скачивания |
| Подмена роли/статуса/ставки | Разрешённые поля ModelForm; staff только из User; переходы только в services | Тест роли и продуктовых лимитов |
| CSRF | Django middleware и токен на всех POST, включая вход/выход; нет csrf_exempt | Client(enforce_csrf_checks=True) |
| XSS | Autoescape, отсутствует safe/mark_safe, клиент использует textContent; CSP без unsafe-inline/eval | Тест комментария со script |
| SQL injection | ORM, параметризованные запросы; пользовательский SQL отсутствует | Ревью запросов |
| Перебор паролей | Сохраняемые в БД лимиты: 10 попыток на аккаунт, 60 на источник за 15 минут; одинаковая ошибка | Тест 429; Django password hashing |
| Утечка cookie | HttpOnly, SameSite=Lax, час жизни; Secure при SANDBOX_MODE=false | Настройки и HTTP-тесты |
| Гонки и повторная выдача | Транзакция IMMEDIATE, версия заявки, проверка назначенного сотрудника, идемпотентное принятие | Тест устаревшей версии и двойного принятия |
| Файловые атаки | Ограничение размера/количества, ASCII PDF-сигнатура и EOF, UUID, безопасное имя, бинарное хранение, скачивание attachment/octet-stream/nosniff | Тест HTML под видом PDF и большого файла |
| Утечка ошибок/кэш | DEBUG=false, общие 403/404/500, no-store | HTTP headers |
| Утечка секретов | Случайный секрет, случайные пароли, .data/.env в gitignore/dockerignore, режим 0600 | Начальная загрузка запрещена вне тестового контура |
| Clickjacking | X-Frame-Options DENY, frame-ancestors none | HTTP-тест |

PDF считается недоверенным даже после проверки сигнатуры. Сигнатура не заменяет антивирус и полноценный парсер. Сервер не выполняет, не рендерит и не распознаёт PDF; MIME скачивания не разрешает открытие встраиваемым просмотрщиком приложения. Для настоящего продукта нужны антивирусная песочница, карантин и политика обработки документов.

Защита от больших запросов: лимит Content-Length 6 МБ до разбора тела, обязательный Content-Length для POST/PUT/PATCH, максимум 1 файл в запросе, 5 МБ для файла и 5 файлов на заявку. Документов на компанию максимум 100 МБ, заявок — 100, активных черновиков — 20. Сетевой reverse proxy должен дополнительно ограничивать тело и скорость чтения — Python middleware не заменяет защиту на периметре. Общего промышленного квотирования хранилища и rate limiting всех операций нет.

При работе за reverse proxy IP-лимит по умолчанию видит IP прокси. Заголовки X-Forwarded-For не принимаются от пользователя. Настройте отдельный edge rate limiter по реальному IP; не начинайте безусловно доверять входящим forwarding headers.

## Перед настоящим развёртыванием

1. Не использовать контрольные данные из отдельной production-БД; установить `SANDBOX_MODE=false`, `DEBUG=false`, уникальный секрет и точные ALLOWED_HOSTS. Настроить TLS.
2. Поставить перед приложением контролируемый reverse proxy. Gunicorn не должен быть доступен в обход прокси. `TRUST_PROXY=true` допустим только когда прокси **перезаписывает** X-Forwarded-Proto, а не пересылает пользовательский.
3. Ограничить тело, время и частоту запросов на периметре. Конфигурация nginx (сертификаты и домен настраиваются владельцем инфраструктуры):

```nginx
client_max_body_size 6m;
client_body_timeout 15s;
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 45s;
}
```

4. Перейти на PostgreSQL и отдельное приватное объектное хранилище; добавить квоты, антивирус и восстановление из резервных копий. Зашифровать диски/бэкапы средствами инфраструктуры. Прикладного шифрования полей в MVP нет.
5. Подключить SSO/MFA сотрудников, восстановление доступа, отзыв сессий и более детальную матрицу полномочий. Сейчас сотрудник видит все отправленные заявки и скачивает их документы; один ответственный принимает решение.
6. Защитить журнал от изменения администраторами приложения/БД, реализовать полную историю снимков, retention и аудит скачиваний. Сейчас журнал фиксирует изменения заявок, а не все чтения данных.
7. Провести интеграционные, конкурентные, нагрузочные тесты, аудит зависимостей и независимый pentest. Настроить мониторинг, алерты и резервные копии. `manage.py check --deploy` должен выполняться с production-настройками.

Законодательное соответствие, банковские нормативы, юридически значимая электронная подпись и реальная выдача средств не заявляются. Отдельная правовая оценка потребуется при переходе к настоящим данным и операциям.

## Скоринговые данные

JSON доступен только сотруднику. Ограничены размер, вложенность и число значений; повторяющиеся ключи и неоднозначные алиасы отклоняются. За клиентом закреплено право вводить финансовые сведения своей заявки, но не результаты внешних проверок. Повторная подача после уточнения помечает оценку как устаревшую: до нового расчёта одобрение и принятие заблокированы.
